# Model card: Neural Guardian `v1.1-logreg-paysim`

## Intended use

Neural Guardian gives an **advisory** fraud-risk score, with its reasons, before an AURIX payment is
confirmed: AUR transfers, escrows and PayPal orders. It never validates, blocks or modifies a
transaction. Every response has `advisory_only: true`, and the user decides.

## Model

- **Model:** L2-regularised **logistic regression** (`C = 1`, class-balanced weights) on standardised features. File: `models/guardian_logreg.json` (means, scales, coefficients).
- **Explanations:** exact SHAP values of a linear model, `coef × (x − mean) / scale` per design-matrix column, summed per feature. The top positive contributions become the `reasons`. A medium or high score always has at least one reason.
- **Probability:** the raw score is mapped to a calibrated probability by isotonic regression fitted on the validation split (`models/guardian_calibration.json`). `risk_score` is that calibrated probability.
- **Levels** are decided on the raw score, with thresholds chosen on validation:
  - `medium` = highest threshold reaching **recall ≥ 95 %**;
  - `high` = lowest threshold reaching **precision ≥ 90 %**;
  - the code enforces `high ≥ medium`.
- **Why not LightGBM** (model v1.0): under the leakage-free protocol below, its validation PR-AUC varied from **0.004 to 0.81 across 5 training seeds** (mean 0.19, standard deviation 0.35). It was rejected by the pre-registered selection rule: the best validation PR-AUC among candidates whose seed standard deviation is ≤ 0.02. The v1.0 numbers (ROC-AUC 0.978, PR-AUC 0.939) came from a 2-way split whose thresholds were chosen on the test set, and are **superseded**.

## Training data

**PaySim** (Kaggle [`ealaxi/paysim1`](https://www.kaggle.com/datasets/ealaxi/paysim1), CC BY-SA 4.0):

| Item | Value |
| --- | --- |
| Transactions | 6,362,620 mobile-money transactions over 744 hourly steps |
| Fraud | 8,213 labelled fraud (0.13 %) |
| Origin | Generated by the PaySim simulator, calibrated on real aggregated logs of a mobile-money service (Lopez-Rojas et al., 2016) |
| File | SHA-256 `16910f90577b0d981bf8ff289714510bb89bc71bff7d3f220f024e287e4eea6b` |

This is not AURIX or PayPal data. Kaggle was not reachable from the build environment, so the
byte-identical file was fetched from a public Git LFS copy and verified by SHA-256
(`training/fetch_paysim.sh`).

## Features

Scale-free features known before confirmation (`app/features.py`):

| Feature | Meaning |
| --- | --- |
| `amount_to_balance` | amount / sender balance before the payment (capped at 10; missing → 0 + missing indicator) |
| `drains_account` | 1 if the payment empties the balance exactly (ratio within 1 %) |
| `tx_type` | one-hot: TRANSFER / CASH_OUT (AUR transfer, escrow) / PAYMENT (PayPal merchant order) / … |
| `sender_prior_txs` | payments previously sent by this sender |
| `amount_vs_sender_avg` | amount / mean of the sender's previous amounts (capped at 10; missing → 0 + indicator) |
| `recipient_prior_txs` | payments previously received by this recipient |

`hour` (a PaySim artefact) and the absolute amount (a different currency scale) are excluded.

## Evaluation protocol (`training/evaluate.py`, research plan step 2.1)

| Split | PaySim steps | Used for |
| --- | --- | --- |
| Train | 1–400 (5,787,030 tx, 4,477 fraud) | fitting the models |
| Validation | 401–550 (378,989 tx, 1,588 fraud) | model selection, thresholds, calibration |
| Test | 551–744 (196,601 tx, 2,148 fraud, 1.09 %) | **read once** at true prevalence |

Ranking metrics and thresholds use the raw score: isotonic calibration flattens the top of the range
into ties, which would distort PR-AUC. Ties are handled by scikit-learn's tie-aware metrics. 95 %
confidence intervals come from a stratified bootstrap (1,000 resamples) of the test set.

Reproduce (about 5 minutes):

```bash
pip install -r requirements-train.txt
```

```bash
python -m training.evaluate /tmp/paysim.csv --seeds 5 --bootstrap 1000 --ship
```

Raw results: `research/results/raw/ml-eval/20261107T204559Z-689045a/`.

## Protocol deviation (reported)

The first threshold rules (`medium`: recall ≥ 0.90, `high`: false-positive rate ≤ 0.001) produced a
`high` threshold *below* the `medium` one, which inverted the levels. They were replaced by the rules
above, which fix the meaning of the levels. The test results of that first run had been seen, so the
reported level metrics are not strictly pre-registered. Ranking metrics (ROC-AUC, PR-AUC) and model
selection are unaffected. This is logged in `CONFIG["protocol_deviations"]` and in the results file.

## Limitations

- **The business rules alone reach PR-AUC 0.938.** PaySim's fraud is the single, easy pattern "empty the account by TRANSFER, then CASH_OUT, to a fresh recipient". The model's margin over the rules (+0.035) is the honest measure of what learning adds here, and real fraud is more varied.
- **Counter-intuitive coefficient.** `amount_to_balance` has a negative coefficient outside an exact drain, so spending 5 % of a balance scores higher than spending 95 % (without draining it). This is learned from PaySim, not a product rule.
- **No fraud in `PAYMENT`.** PayPal orders map to `PAYMENT`, which has no fraud in PaySim, so they always score low. **No performance is claimed for merchant or PayPal payments.**
- **Simulated data.** PaySim is calibrated on real logs, but the transactions are generated.
- **Short history.** Sender and recipient history comes only from requests seen by this process, in memory.
- **No adversarial robustness or fairness study yet** (research plan, steps 2.2 and 2.3).
