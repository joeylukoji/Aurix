# Model card: Neural Guardian `v1.0-lgbm-paysim`

## Intended use

Neural Guardian gives an **advisory** fraud-risk score, with its reasons, before an AURIX
payment is confirmed: AUR transfers, escrows and PayPal orders. It never validates, blocks or
modifies a transaction. Every response has `advisory_only: true`, and the user decides.

## Model

- LightGBM gradient-boosted trees (binary), 300 rounds. File: `models/paysim_lgbm.txt`.
- Explanations: SHAP values from LightGBM's native TreeSHAP (`pred_contrib=True`). The top positive contributors become the `reasons`. A medium or high score always has at least one reason.
- Levels: `low` < 0.1 ≤ `medium` < 0.5 ≤ `high`.

## Training data

**PaySim** (Kaggle [`ealaxi/paysim1`](https://www.kaggle.com/datasets/ealaxi/paysim1), CC BY-SA 4.0):

| Item | Value |
| --- | --- |
| Transactions | 6,362,620 mobile-money transactions over 744 hourly steps (30 days) |
| Fraud | 8,213 labelled fraud (0.13 %) |
| Origin | Generated by the PaySim simulator, calibrated on real aggregated logs of a mobile-money service in an African country (Lopez-Rojas et al., 2016) |
| File | `PS_20174392719_1491204439457_log.csv`, SHA-256 `16910f90577b0d981bf8ff289714510bb89bc71bff7d3f220f024e287e4eea6b` |

This is not AURIX or PayPal data. Kaggle was not reachable from the build environment, so the
byte-identical file was fetched from a public Git LFS copy and verified by SHA-256 (see
`training/fetch_paysim.sh`).

Reproduce:

```bash
training/fetch_paysim.sh /tmp/paysim.csv
```

```bash
pip install -r requirements-train.txt && python -m training.train_paysim /tmp/paysim.csv hour,log_amount
```

## Features

These are scale-free features that the gateway knows before confirmation (`app/features.py`):

| Feature | Meaning |
| --- | --- |
| `amount_to_balance` | amount / sender balance before the payment (capped at 10; missing if unknown) |
| `drains_account` | 1 if the payment empties the balance exactly (ratio within 1 %) |
| `tx_type` | TRANSFER (AUR transfer, escrow) or PAYMENT (PayPal merchant order) |
| `sender_prior_txs` | payments previously sent by this sender |
| `amount_vs_sender_avg` | amount / mean of the sender's previous amounts (capped at 10) |
| `recipient_prior_txs` | payments previously received by this recipient |

**Deliberately excluded:**

| Excluded | Why |
| --- | --- |
| `hour` | A PaySim artefact: fraud is spread evenly over 24 h while legitimate traffic follows a daily cycle, so "night" alone predicts fraud. It was the top feature when included. |
| Absolute amount | PaySim amounts are on a different scale from AUR or USD demo amounts. A model using them scored a 100 % drain of 100 AUR as 0 % risk. Without them, the test metrics improved. |
| Post-transaction and destination balances | They leak the outcome or are simulation artefacts. |

## Evaluation (out-of-time, true prevalence)

Train: steps 1–500 (6,061,807 transactions, 5,561 fraud). Test: steps 501–744 (300,813
transactions, 2,652 fraud, 0.88 % prevalence, not resampled).

| Metric | Value |
| --- | --- |
| ROC-AUC | **0.978** |
| PR-AUC (average precision) | **0.939** |

| Threshold | Precision | Recall | Share of payments flagged |
| --- | --- | --- | --- |
| 0.1 (`medium`) | 0.961 | 0.950 | 0.87 % |
| 0.5 (`high`) | 0.964 | 0.918 | 0.84 % |
| 0.7 | 0.989 | 0.524 | 0.47 % |

Full numbers: `models/paysim_metrics.json`.

## Limitations

- **PaySim's fraud is easy to detect.** Fraud there is almost always "empty the account by TRANSFER, then CASH_OUT, to a fresh recipient". Real fraud is more varied, so expect much lower performance on real traffic.
- **Simulated data.** PaySim is calibrated on real logs, but the transactions themselves are generated.
- **PayPal orders.** They map to PaySim `PAYMENT`, which contains no fraud, so they always score low. A real PayPal risk model would need PayPal-specific data.
- **Short history.** Guardian learns sender and recipient history only from the requests it sees, in memory, and loses it on restart. A production version would read history from the chain index.
- **No fairness or robustness audit**, and no protection against an adversary who knows the features.
